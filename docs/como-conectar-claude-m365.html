Instalación

Proceso de configuración

1

Registrar la app en Azure

Accede a portal.azure.com → App Registrations → New registration.

  • Nombre: ClaudeMCP
  • Supported accounts: Multitenant + personal Microsoft accounts
  • Plataforma: Aplicaciones móviles y de escritorio
  • Redirect URI: http://localhost:3000
  • Activar: Allow public client flows = Yes
2

Configurar permisos de Graph API

En API permissions → Add permission → Microsoft Graph → Delegated. Añadir los 15 permisos necesarios (ver tabla más abajo).

3

Instalar y compilar el servidor

git clone https://github.com/lfpalomaresg/m365-mcp-server.git
cd m365-mcp-server
npm install
cp .env.example .env
# Editar .env con tu CLIENT_ID
npm run build
4

Autenticación inicial (solo una vez)

npm run auth

Se abre el navegador con el login de Microsoft. Inicia sesión con tu cuenta personal → acepta los permisos → token guardado automáticamente.

5

Registrar en Claude Code

Añadir en ~/.claude.json:

{
  "mcpServers": {
    "m365-personal-suite": {
      "command": "node",
      "args": ["/ruta/al/proyecto/dist/index.js"]
    }
  }
}

Reiniciar Claude Code. ¡Listo!

Obstáculos y cómo los resolvimos

El camino real no fue lineal. Estos son todos los problemas que encontramos y cómo los sorteamos:

Error 1 Azure Portal bloqueado por popup de tokens

Al intentar acceder a portal.azure.com con la cuenta personal, un popup bloqueaba la navegación impidiendo llegar a App Registrations.

Solución: Usar Safari en modo de navegación privada. El gestor nativo de Microsoft en Safari evita el conflicto de sesiones que Chrome genera con cuentas múltiples.
Error 2 aka.ms/appregistrations — portal deprecado

El portal simplificado para cuentas personales mostraba "esta operación está en desuso" sin permitir crear nuevas apps.

Solución: Abandonar ese portal y buscar alternativas (Azure gratuito, Developer Program, cuenta corporativa).
Error 3 Microsoft 365 Developer Program — no elegible

"You don't currently qualify for a Microsoft 365 Developer Program sandbox subscription." Microsoft ha restringido el acceso a este programa.

Solución: Usar la cuenta de trabajo para registrar la app en Azure, configurándola para soportar también cuentas personales.
Error 4 CLIENT_ID público de Microsoft — first party restriction

"The application is a first party application, the user does not have consent, and users are not permitted to consent to first party applications." El CLIENT_ID de Azure PowerShell (1950a258...) fue bloqueado.

Solución: Registrar una app propia en Azure usando la cuenta corporativa del usuario, configurada para multitenant + cuentas personales.
Error 5 Device Code Flow — invalid_grant persistente

Tras registrar la app correctamente, el Device Code Flow devolvía invalid_grant y post_request_failed. El mensaje del device code aparecía como "undefined".

Causa raíz: El toggle "Allow public client flows" no estaba activado en Azure → sin él, Microsoft rechaza el intercambio de token del Device Code Flow.
Problema 6 Device code expirando antes de usarlo

Incluso tras activar el toggle, el código expiraba al intentar introducirlo en microsoft.com/devicelogin debido a problemas de timing con el authority "consumers".

Solución: Abandonar Device Code Flow completamente y migrar a PKCE con servidor HTTP local — más fiable, sin códigos manuales y sin expiraciones.
Problema 7 Redirect URI — https vs http

El URI se guardó como https://localhost:3000 (con S) en vez de http://localhost:3000. El servidor local no tiene SSL, por lo que no coincidía.

Solución: Borrar la URI incorrecta y añadir exactamente http://localhost:3000 (sin S).
Problema 8 Redirect URI bajo plataforma incorrecta

La URI http://localhost:3000 se añadió bajo la plataforma "Web" (para apps confidenciales con client secret) en vez de "Aplicaciones móviles y de escritorio" (para public clients con PKCE).

Solución: Mover el URI a la sección "Aplicaciones móviles y de escritorio". Las URIs de tipo Web no son válidas para public clients sin client secret.
Éxito PKCE + Mobile/Desktop platform = autenticación exitosa

Con la combinación correcta: PKCE Flow + Allow public client flows activado + URI bajo Mobile/Desktop platform + authority "common".

Resultado: Autenticación completada, token guardado en caché, servidor MCP operativo y registrado globalmente en Claude Code.
Fix · Jun 2026 "No active session found" pese a haber autenticado con éxito

Semanas después, todas las herramientas (p.ej. get_latest_emails) empezaron a devolver "No active session found. Run 'npm run auth'". Lo desconcertante: npm run auth completaba el login correctamente y escribía el token, pero el server seguía sin verlo.

Causa raíz: Claude Code lanza el server MCP desde un CWD arbitrario (el $HOME del usuario), no desde la carpeta del proyecto. Con TOKEN_CACHE_PATH=.token_cache.json (ruta relativa), npm run auth escribía el token en proyecto/.token_cache.json pero el server lo buscaba en ~/.token_cache.json → nunca lo encontraba.

Solución: el código resuelve ahora TOKEN_CACHE_PATH a ruta absoluta anclada a la raíz del proyecto (__dirname/..), y se recomienda definir una ruta absoluta en .env. Regla general: un server MCP nunca debe depender del CWD.
Cronología

Evolución de la estrategia de autenticación

Intento 1 — Microsoft PUBLIC CLIENT_ID (Azure PowerShell)

Usar el CLIENT_ID público 1950a258... para evitar registrar una app. Bloqueado por restricción de seguridad de Microsoft.

Intento 2 — Device Code Flow con app registrada

App propia registrada correctamente pero el intercambio de token fallaba con invalid_grant. Causa: faltaba "Allow public client flows".

Intento 3 — Device Code Flow con toggle activado

El mensaje del device code aparecía, el usuario completaba el login, pero los códigos expiraban por problemas de timing con la autoridad consumers.

Solución final — PKCE con servidor HTTP local

Flujo PKCE: el servidor arranca un listener en localhost:3000, abre el navegador automáticamente, captura el auth code en el redirect y lo intercambia por token. Sin códigos manuales, sin expiraciones.
